# M5 T152 S1: Capture The MS-DOS MEM CPU Fault

## Objective

Turn the local MS-DOS `MEM` invalid-opcode observation into bounded,
machine-owned evidence. Establish the exact first CPU fault before choosing an
instruction repair.

## Scope

- Add a fixed-capacity in-memory execution window and first-fault snapshot to
  `core/machine`; `core_machine` is their sole owner.
- Expose copied diagnostic data through a `core_machine` interface suitable for
  a debugger or project-owned smoke, without exposing mutable executor state.
- Add a Windows FDD smoke that boots the supplied local image, injects
  `mem<Enter>` through the existing Win32 keyboard ingress, and reports the
  first bounded fault or a bounded non-fault outcome.
- Record the observation, including instruction bytes/prefixes, registers,
  FLAGS, exception mask/code, recent execution window, elapsed time, and
  no-progress outcome.

## Non-Goals

- No CPU instruction semantic change, BIOS/DOS workaround, capability claim,
  default trace file, Bochx import, or VDM runtime work.
- No guest media, guest output, raw trace, machine-local path, or third-party
  code is committed.

## Contracts And Rules

- `RULES.md`: core owns guest mechanics and has no VM/VDM dependency; one
  state owner; fixed bounded diagnostics; no global/TLS/current-object
  selection; one task artifact only if a runnable path changes.
- `docs/requirements/cpu-verification.md`: #UD is captured and classified,
  never suppressed or converted to a successful no-op.
- `docs/planning/execution-policy.md`: the observation has instruction,
  wall-clock, and no-progress budgets; no raw recorder is enabled.

## Baseline And Inputs

- Baseline: `fcf97b2` (`nxvm_0_5_0151.exe`), which boots the local FDD fixture
  and proves guest keyboard ingress with `ver<Enter>`.
- Local-only input: the owner-supplied FDD image passed as the smoke argument.

## Verification

1. GCC builds a focused core fault-capture smoke and the local `MEM` fixture
   smoke.
2. The core smoke proves that the execution window wraps at its declared
   fixed capacity and that the first fault snapshot remains stable.
3. The local fixture smoke runs no longer than five seconds after launch,
   records a first fault or explicit bounded no-fault/no-progress verdict, and
   never writes a raw trace file.
4. Existing FDD DOS-prompt, keyboard, Console, debugger, dependency, and
   session gates remain valid.

## Stop Conditions

Stop rather than repair if fault capture requires VM/VDM policy in core,
creates a second executor or mutable mirror state, introduces unbounded output,
changes retained Console/debugger/startup behavior, or cannot boot the known
FDD fixture within its established three-second prompt budget.
