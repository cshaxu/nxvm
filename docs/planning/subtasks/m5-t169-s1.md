# M5 T169 S1: RAM Cold Reconfiguration And Lifecycle Design

## Objective

Replace the temporary T165 whole-`vm_session` reconstruction design with a
bounded core-owned RAM cold-reconfiguration plan. No runtime code changes in
this task.

## Frozen Decisions

### Lifecycle

`INITIALIZED` is the open provider/configuration window. `STOPPED` means a
completed reset with no guest execution in progress, including the first state
visible before `START`. It is always cold-start-ready: CPU, RAM, shared
devices, frozen providers, and reset vector are complete; the next run needs
no intermediate initialization. `RUNNING` exists only inside
`core_machine_run`. `PAUSED` is a returned post-execution/debug boundary,
never the initial/reset state. `FAULTED` requires an explicit reset.

`core_machine_reset` will end in `STOPPED`; `core_machine_run` will accept a
stopped cold start or a paused continuation. `DEVICE RAM` must require core
lifecycle `STOPPED`, a non-running VM control state, and no active platform run
handle. It does not silently wait, pause, or stop a running guest. A running
stop or reset request completes the same cold reset before publishing
`STOPPED`; a reset failure remains faulted rather than creating a limbo state.

### RAM

`t_ram` gains distinct installed-byte and backing-capacity facts. The current
unmapped core treats only `[0, installed_bytes)` as ordinary RAM. Crossing or
addressing outside that range is a deterministic access failure, never modulo
foldback. The existing high-address special case is not a profile mapping and
must not remain an implicit alias. A future ROM/hole mapping must be an
explicit provider contract.

No profile/provider/debugger code may cache a RAM backing address. It may keep
its already-owned `t_ram *` and use checked read/write/copy operations. The
pointer-returning real-address helper is migration debt and must leave all
provider call paths before RAM shrinking is enabled.

### Cold Reconfiguration

`core_machine_reconfigure_memory(machine, bytes)` is core-owned and accepts
only `STOPPED` machines with frozen topology. It validates the capacity,
replaces the one RAM backing allocation, updates installed bytes, clears RAM,
and invokes the normal cold reset sequence. The same `core_machine`, CPU,
PIC/PIT/DMA/KBC/VADP, provider registrations, VM devices, media mounts,
platform handle, debugger context, and session ID remain alive. Guest RAM,
registers, device registers, trace state, and firmware-initialized guest state
are reset.

CPU/FPU model, ROM/profile, port/IRQ topology, and provider graph stay frozen;
their change requires a new `SESSION OPEN`. A future `SESSION OPEN --from`
copies configuration and media descriptors only, never guest state.

## Applicable Rules

`RULES.md`: machine/session rules, explicit ownership, no raw provider backing
pointers, task artifact policy, retained Console/debugger/FDD behavior, and
one active subtask. `docs/architecture/contracts.md` remains the public
contract authority.

## Non-Goals

No new DOS behavior, VDM runtime, ROM mapper, CPU/FPU/profile hot switch,
media-policy change, platform-handle redesign, session cloning, or user-visible
Console grammar change.
