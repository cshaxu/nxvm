# M1 T1 S1: Baseline The Full NXVM Machine

## Objective

At subtask start, record and import the then-current sibling NXVM `HEAD` into an
explicitly temporary baseline area. Build it with the default GCC toolchain,
reproduce current machine initialization and text-mode boot/execution behavior
using the recorded `fdd.img`, `hdd.img`, `stop.com`, and `reset.com` local
fixtures, and establish evidence before making subtractive changes.

## Non-Goals

Do not implement an owned DOS backend, host-drive mapping, product CLI, new
graphics/device behavior, Microsoft component research code, or modify the
sibling NXVM checkout. Do not claim redistribution rights for, or commit,
local image fixtures.

## Entry Conditions

1. Confirm the M0 GCC smoke record applies to the active checkout.
2. Pin the NXVM source revision at the current `HEAD` and create one provenance record per imported
   or substantially derived source unit, including a generated per-file
   manifest for a whole-baseline import.
3. Verify the local fixture identities in
   `docs/fixtures/m1-local-images.md`; keep them read-only and outside the
   repository.
4. Document the full baseline's C11 portability boundary before changing its
   behavior. NXVM's MSVC-specific type spellings, including `unsigned __int64`,
   must be normalized in a project-owned compatibility header rather than
   bypassing `_WIN32` or modifying the sibling checkout.
5. Create the M1 experiment record defined below and freeze its FDD/HDD
   checkpoints, budgets, and expected markers after the first raw baseline
   observations and before declaring M1 complete.

## Expected Surface

- `src/nxvm-baseline/` receives the imported whole baseline without new product
  behavior, including the existing Win32 and Linux platform source.
- after an unmodified baseline observation, only proven irrelevant Bochs bridge
  code and repository-only metadata may be removed; attribution, provenance,
  and independent third-party notices remain.
- `tests/baseline/` receives repeatable build and boot/execution observations;
  later focused tests may enter `tests/machine/`.
- project-owned machine trace interfaces may be added behind a disabled-by-
  default test build option; any reference adapter stays in research tooling.
- `THIRD_PARTY_NOTICES.md`, provenance records, and the local-fixture record
  reflect the import and test inputs.

## Verification

- compiler and probe smoke commands from `docs/build/toolchain.md`;
- a full-baseline GCC target with a recorded warning inventory;
- the Windows GCC run is the M1 acceptance target; retained Linux source is not
  yet a Linux build or release commitment;
- FDD and HDD fixture runs record configured devices, expected checkpoints or
  stop reasons, text or window output, reached state, and instruction/time/no-
  progress budgets using the frozen experiment record; `stop.com` and
  `reset.com` are used only after that record classifies a lawful guest-visible
  placement and expected semantics;
- the generated M0 COM probe may be an optional baseline workload only when a
  local fixture can lawfully load it; it is not an M1 exit condition;
- focused follow-up tests preserve each behavior when code begins to move out
  of `src/nxvm-baseline/`.
- a differential experiment, when used, has its own record and enforces its
  trace checkpoint and watchdog budgets.

## Stop Conditions

Stop and request direction if the full baseline cannot compile without an
unbounded compiler workaround, the fixtures do not match their recorded hashes,
their legal status prevents local use, required behavior depends on an
undocumented Windows mechanism, or required source/license notices are missing.

## Experiment Record

Record ntvdm64/NXVM revisions; GCC, CMake, Ninja versions and executable hashes;
Windows edition/build; fixture identities; exact device configuration; accepted
checkpoint or stop reason; display/trace marker; and instruction, wall-clock,
and no-progress budgets.

Use the imported NXVM Console workflow, with only local paths substituted:

```text
device display console
device fdd insert <fdd.img>
set boot fdd
start
```

```text
device display console
device hdd connect <hdd.img>
set boot hdd
start
```

Before any DOS payload is tested, record the NXVM Console `load` command form,
lawful guest-visible placement, launcher, expected behavior, and cleanup. The
local `stop.com` and `reset.com` names do not define their semantics and do not
form an M1 exit condition until this record classifies them.
