# M5 T161 S1: VM Provider Composition Separation

## Objective

Replace the mixed-purpose `vm/composition/session/providers.*` implementation
with three honest responsibilities while retaining its exact full-PC order:

1. VM-only device lifecycle: CMOS, FDD, FDC, and HDD.
2. Default-profile firmware lifecycle and BIOS registration.
3. A thin session provider-lifecycle coordinator that preserves the existing
   interleaving and remains the sole `core_machine_execution_provider` bridge.

`block.c` and `display.c` remain separately owned provider bindings. The
coordinator does not own generic core devices, an instruction loop, profile
selection, Console policy, or a second session.

## Scope

- Split implementation files and headers by the three responsibilities.
- Retain existing `vm_session_providers_*` call surface only as the
  coordinator, or rename it only where every direct caller moves together.
- Preserve device/firmware initialization, reset, refresh, and finalization
  order byte-for-byte at their public calls.
- Add a static source-shape check which rejects a re-merged mixed provider
  implementation.

## Non-Goals

No device behavior, BIOS/POST/IVT order, media policy, provider phase, UI,
threading, or core lifecycle change.

## Rules And Gates

Applicable `RULES.md` rules: composition-only integration, file names match
responsibility, one core lifecycle owner, no duplicate executor/session,
retained NXVM behavior, artifact hygiene.

Run Windows GCC and the source-shape gate, then Console lifecycle, debugger,
and FDD DOS-prompt gates. Stop for review if FDD boot, BIOS services, Console
grammar, debugger behavior, or provider callback order changes.
