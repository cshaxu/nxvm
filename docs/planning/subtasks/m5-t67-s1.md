# M5 T67 S1: RAM And Port Bus Instance Authority

Status: active.

## Objective

Replace the retained RAM and port selected-object aliases with explicit
composition-owned references. The CPU execution context receives the same RAM
and port objects already owned by `vm_composition_live_machine`; no buffer,
port table, or I/O latch may be copied.

## Ordered Parts

1. Add explicit RAM/port references and lifecycle operations, then move CPU
   physical-memory and I/O paths to them.
2. Define and exercise the explicit port-dispatch ABI. Device callback bodies
   migrate in T68/T70 because they own those devices; the temporary callback
   compatibility layer remains forwarding-only until T73.
3. Move composition, debugger, and direct core-bus callers; leave device
   handler bodies for their owning T68/T70 tasks only after their callback
   context is explicit.
4. Add two-context RAM/port isolation coverage and record remaining later
   device/profile compatibility callers for T68--T72. T73 deletes aliases.

## Invariants

- The live machine remains the only storage owner for `t_ram` and `t_port`.
- Memory allocation, A20 behavior, I/O width/latch behavior, reset order,
  device registration order, BIOS operation, and Console UX do not change.
- A handler cannot discover a RAM or port object through a current-object
  lookup. It receives an explicit context or provider binding.
- No new `vram`, `vport`, `*_current`, or `*_bind_live` caller is allowed.

## Initial Map

- CPU physical-memory helpers currently call `vramReadPhysical` and
  `vramWritePhysical`; CPU I/O instructions exchange width-specific values
  through `vport.data`.
- RAM owns allocation, reset, A20 wrapping, and real-mode convenience access.
- Port owns the dispatch tables and the I/O value latch; device callbacks use
  that latch today, so the callback ABI change must precede device migration.

## P1 Evidence

The CPU execution context now references the same live-machine RAM and port
objects as its CPU and decoder. CPU physical-memory reads/writes call explicit
RAM operations rather than the selected `vram` object. RAM has explicit
physical, real-mode, and allocation operations; legacy calls forward to them.
The focused CPU-context build and isolation smoke pass. No port callback body
has moved in P1.
- Composition owns RAM/port initialization, reset, refresh, finalization, and
  the retained Console RAM-size report.

## Gates

GCC and dependency-DAG; RAM/port authority and CPU probe/stop smokes;
debugger/Console; FDD/HDD full-PC profile; a two-context RAM/port isolation
smoke; then `build/output/nxvm_0_5_0067.exe`.
