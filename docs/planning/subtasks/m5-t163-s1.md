# M5 T163 S1: Frozen Core API Boundary Design

## Objective

Design the replacement for raw mutable core borrows used outside approved
composition binding and debugger adaptation. Decide how retained `DEVICE ram`
is represented without mutating a frozen/running machine, and define copied
CPU/diagnostic observation at an explicit execution boundary.

## Non-Goals

No implementation, raw-borrow deletion, Console grammar change, machine
reconstruction, media-policy change, or CPU behavior change.

## Exit

Record the exact API/lifetime/state transition, compatibility path, tests, and
stop conditions for a bounded implementation task. Preserve the retained NXVM
Console, debugger, FDD boot, and multi-session semantics.

## Approved Design

### Two Deliberate Core Boundaries

1. **Configuration borrow.** A composition may obtain mutable executor and
   shared-device implementation objects only while its `core_machine` is
   `INITIALIZED` and before provider freeze. Such a borrow is for immediate
   provider/profile binding only. It is not a transferable handle, may not be
   stored in a session field, may not be used by a product command, and expires
   when `core_machine_freeze_execution_providers()` succeeds. The eventual API
   names this purpose explicitly as a configuration borrow; the historical
   `core_machine_executor_*_borrow` names are transitional and must disappear.
2. **Paused copied observation.** A caller obtains lifecycle, CPU state, and
   first-fault diagnostic as copied data only after `core_machine_run()` has
   returned and lifecycle is `PAUSED`, `STOPPED`, or `FAULTED`. It cannot read
   a live register/diagnostic object while the execution thread owns it.
   `core_machine_get_cpu_state()` and `core_machine_get_cpu_diagnostic()` gain
   this same state guard; a combined copied observation payload prevents a UI
   from combining values from different quanta.

The existing direct debugger target remains a narrow transitional adaptation:
it is constructed by root composition, targets one explicit `vm_session`, and
is entered only after the VM control boundary has confirmed pause. T164 adds
the core guard and an adapter assertion before later work replaces its
implementation-level accesses with explicit debug operations. This is not a
general product or platform escape hatch.

### Retained `DEVICE ram` Semantics

RAM capacity is frozen `core_machine_config.memory_bytes`, not mutable RAM
contents. `DEVICE ram <size>` retains its grammar and selected-session
semantics but becomes a synchronous, stopped-session reconfiguration:

1. Reject a running, pausing, faulted, or otherwise non-quiescent session with
   a defined Console error; never wait while retaining a raw RAM pointer.
2. Build a candidate `vm_session_machine_config` from the selected session's
   frozen CPU/FPU/profile/boot policy and its current media descriptors, with
   only `memory_bytes` changed.
3. Construct and freeze one replacement `core_machine`, VM-only devices, and
   default-profile firmware through the existing lifecycle order. Do not copy
   guest RAM, CPU, ports, controller registers, trace, debugger state, or
   provider objects into it.
4. If construction or media reattachment fails, destroy only the candidate and
   leave the old stopped machine untouched. If it succeeds, finalize the old
   machine/device graph in its documented reverse order, install the candidate
   into the same `vm_session`, and reset it.

The `vm_session` remains the only concrete session object and keeps its opaque
manager entry, Console target, platform context, run handle, and numerical ID.
There is never an old and new runnable machine at the same time. A successful
reconfiguration intentionally discards guest execution state and starts at the
normal reset vector; that is the safe equivalent of changing physical RAM.

Media descriptors must be composition-owned, copied values, not borrowed path
pointers. Their exact host-policy cleanup is T166; T165 only preserves an
already attached explicit FDD/HDD image when reconstructing a session.
