# M5 T14 S3: Core-To-VM Dependency Removal

## Objective

Remove the approved core-to-VM/default-profile dependencies through core
contracts and VM root-composition bindings, without changing retained NXVM
Console, debugger, boot/media, or task-artifact behavior.

## Initial Slice

Move the legacy `vmachine` lifecycle sequence by `git mv` from
`src/vm/machine/vmachine.c` to `src/vm/composition.c`. Preserve its init,
reset, refresh, and final statement ordering exactly; repair only its direct
source/CMake path. Its old header remains temporarily in place until the
following focused move. This relocation makes the existing composition logic
visible without claiming that the composition refactor is complete.

## Non-Goals

Do not alter a device implementation, provider callback, BIOS/POST/IVT order,
Console grammar, debugger behavior, platform input/output behavior, media
behavior, C type names, or executable identity. Do not create a VDM executable.

## Reference And Gates

The reference is `126eb22` and the approved map is
`../m5-t14-s2-migration-map.md`. Before the next source move, run the
dependency-DAG target, the relevant GCC build, the VM composition/profile
smokes, retained Console/debugger gates, and bounded FDD/HDD reset-vector
evidence when a full-PC path is affected.

## Stop Condition

Stop for owner approval before any required change to lifecycle ordering,
legacy global-state lifetime, BIOS/POST ordering, or an observable NXVM
interaction.

## Initial Slice Evidence

`src/vm/machine/vmachine.c` was moved unchanged to `src/vm/composition.c` and
the legacy lifecycle target path was repaired. The dependency source allowlist
decreased from 50 to 49 entries because composition is the permitted product
root. GCC configured successfully; `verify-dependency-dag`, retained Console,
full-PC profile with `../fdd.img ../hdd.img`, and default-profile with
`../fdd.img` passed. `nxvm-m5-t13` also rebuilt successfully with the moved
source. No new task artifact is due until M5 T14 itself completes.

The unchanged legacy execution loop and command-boundary owner then moved from
`src/vm/machine/device.c` to `src/vm/composition_loop.c`; only its CMake path
changed. The same dependency, Console, FDD/HDD profile, default-profile, and
task-artifact build gates passed. `device.h` remains temporarily at its legacy
machine path because Console/debugger callers still use its broad API; its
public control surface is the next audited boundary, not a mechanical header
move.

The unchanged start/reset/stop/resume and platform lifecycle wrapper then moved
from `src/vm/machine/machine.c` to `src/vm/composition_machine.c`. This removed
the direct machine-to-platform source edge, reducing the checked allowlist to
48 entries. The same focused GCC, dependency, Console, FDD/HDD profile,
default-profile, and task-artifact build gates passed.

The private lifecycle declaration then moved from
`src/vm/machine/vmachine.h` to `src/vm/composition.h`. Its only two callers,
the root composition lifecycle and loop sources, now include the root header.
The same focused gates passed; no source-edge count changed because this move
removes a same-module legacy header rather than a forbidden cross-owner edge.
