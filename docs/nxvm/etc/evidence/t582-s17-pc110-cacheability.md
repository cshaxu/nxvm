# T582 S17 — PC110 firmware cacheability audit (in progress)

Existing S15 x64 worker IP samples were mapped to the matching executable symbols: firmware read 53/15, firmware query 42/20 and Core cache query 40/27 early/late out of 3,304/3,336 in-image samples. The functions include inlined work, sample attribution is approximate, and these are not inclusive costs. The observation does not by itself prove the significance of a route or cache change.

Task-only counters in the actual PC110 provider on a private-media x64 fixed run reached the same 10,000,000 instructions, 79,964,294 ticks and PC 0003dbc5. In the second instrumented run, firmware query was called 19,827,115 times (18,470,246 read and 1,356,869 write); read was called 15,894,040 times. Read counts reflect callback invocations and per-block decode chunks, not bytes or retired instructions. Read chunks included 15,334,285 internal shadow, 555,657 Flash and 4,098 open bus; 11,192,714 internal chunks started in E/F, 1,584,479 in C/D and 2,557,092 elsewhere. Instrumentation and asynchronous execution affect counts and time; this early fixed-work probe is not a late-workload or desktop performance result.

The provider consults mutable VL82C420 shadow fields, maps internal and external sources independently for reads and writes, and can expose SMRAM; PC110 already signals some decode changes for planar selection, SMRAM and firmware replacement. The generic 486 cache policy currently only admits proven ordinary RAM. Treating provider memory as cacheable would change cache hits and guest timing and must account for all register-driven mapping changes, all access sources, writes, observability and hardware/source confidence. The listed signals alone do not prove complete invalidation, and PC110-EMU and PC110-QEMU located so far do not establish this 486 chipset's cache-enable behavior. No cacheability change or public API is admitted by the observed counts.

Evidence SHA-256 (source categories, regions): `CF0392DF434B666FAE9BE1B990BCBB86432E6C28A36743C444D7A7CA454DB735`, `AF4D55E1E1C9DE61DBD8F403287AEE1A24B9D74BF20B2574C20D664B6AA4DA88`.

Additional static boundary: `mypc110_firmware_decode` reads ECED registers 0x0c and 0x0f onward, while the generic selected ECED data-write path in `pc110_config.c` does not explicitly call `x86_core_machine_signal_memory_decode_change`. Current policy declines CPU cache fills for provider routes, and PC110 does not explicitly enable the Core prefetch reservation used by DeskPro. This is not a demonstrated current failure; it is a concrete reason a future provider-cache proposal cannot assume the existing notifications cover ECED remapping. Any such proposal must first trace all aliases and writes, identify the correct invalidation owner and test changed mappings, including instruction fetch.

The local Open-Source-PC110 `Discovery/Chipset/readme.md` section 13j.5 reports BIOS programming and hardware readback of ECED 0x07 bit 3 and 0x18 FCBL=0xAA, and associates 0x13–0x18 with per-16-KiB cacheability. This is meaningful PC110-specific evidence, but the source expressly combines reconstruction, analog VL82C480 documentation and observations; the precise per-field polarity, all bus-cycle qualifiers and change/invalidation sequencing are not yet established here. Do not label this as a VL82C420 vendor manual or turn it into an unconditional cache fill. A VL82C480 manual concerns a related chip, not by itself proof of VL82C420 behavior.

A separate 252.78-second task-only x64 product-path run sampled ECED fields on selected F-segment read callbacks, without changing them. At F-read 1 the observed MISCSET/FAXS/FCBL were EC/00/00; at 10,000 they were E4/00/55; at 1,000,000, 5,000,000 and 10,000,000 they were E4/AA/AA; at 50,000,000 they were EC/AA/AA. The latter occurred between published guest ticks 416,870,145 and 421,548,886. The run exited zero at 695,936,522 reported ticks, RTC second 21 and a 640x480 sampled frame. Counters and logging perturb scheduling; callback-count checkpoints are not exact guest timestamps and do not capture every register transition. This confirms that the owner's proposed cacheability investigation must distinguish an early disabled and a later enabled phase according to the Open-Source-PC110 interpretation of MISCSET bit 3. The present Core query consults CR0/page attributes and route policy but does not consume this PC110 register. This is an observed implementation boundary, not proof that all PC110 cache-enable semantics have been implemented or that changing the model will speed up the host.

Log SHA-256 (run summary, output): `2EE9BC3C8F4ECE98759F0F25451F9B4D1EEB2EDF12ECDE6FB1893062587324A6`, `F6D1C10EB6E53A6E4979D14C220BB9A31384DFADA88C21736E8EB7BDA49A6857`.

The observed FAXS value AA is particularly significant: the current PC110 decode treats each two-bit field 2 as internal reads and external writes. Its firmware write callback writes shadow only when the write-side decode selects internal; an external Flash write currently leaves shadow unchanged. The existing 486 cache write-hit path, however, updates its cached bytes after a successful bus write. Merely marking this provider cacheable can therefore make a later read differ from the provider read view after a guest write. This is a concrete source-level counterexample to a cacheability-only change, not a dynamically reproduced current regression: the current provider is excluded from cache fill. A viable model needs an explicit, tested ownership rule for asymmetric write mappings and dynamic invalidation, in addition to MISCSET/FCBL gating.
