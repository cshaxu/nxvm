# T582 S22 — Cache-hit copy and compiler audit

S15 samples included the Types memory-copy facade, but did not establish which whole call was costly. A scratch-only CPU candidate specialized the two existing cache-read copies for lengths 1, 2, 4 and 8 using constant-size `lib_memory_copy`, with the existing variable-size operation as fallback. It retained alignment and aliasing safety and did not change routing. On a single sequential pair per width at 10,000,000 retired instructions, 79,964,294 ticks and PC 0003dbc5, x64 baseline/candidate elapsed 18,915/18,950 ms and x86 22,752/22,743 ms. The near-equal results do not justify adding branches and a helper; the candidate was rejected without a production change or long run. This is not an exhaustive semantic equivalence result.

A separate build-only experiment compiled five existing X86 Core CPU/memory translation units with GCC `-flto` as scratch objects and linked them ahead of unchanged production archives; it did not change the project build or test a full LTO configuration. All four probes reached the same checkpoint. In baseline-then-candidate order, x64 measured 18,895/17,988 ms and x86 23,407/22,245 ms. In reversed candidate-then-baseline order, x64 candidate/baseline measured 21,778/20,262 ms and x86 24,204/25,369 ms. The x64 direction reversed and build/link overhead increased; neither universal improvement nor sustained benefit is established. No LTO setting was introduced. These sequential measurements are susceptible to host variation and do not support conclusions about another compiler or complete LTO.
