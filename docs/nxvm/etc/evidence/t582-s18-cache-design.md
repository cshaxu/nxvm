# T582 S18 — Provider cache design (in progress)

## Confirmed boundaries

The existing `x86_core_cpu_cache_memory` reports decoded address and fill eligibility; the Core currently declares only proven ordinary RAM eligible. A provider can independently implement instruction reads and data reads, so its registration alone cannot prove one shared CPU cache line has identical contents for fetch and data. The PC110 firmware currently has a normal read callback and dynamically selected shadow, Flash and open-bus views. The separate `memory_cache_control` board callback observes admitted external bus cycles and returns status; it does not return KEN/fill eligibility and is not a substitute for a cacheability contract.

A potential generic opt-in must prove the entire 16-byte line resolves to the same provider and physical view, ensure fetch/data equivalence and absence of read side effects, and default every existing unannotated provider to non-cacheable. The 486 write-hit implementation updates its cache after the bus write; a successful write may update a resident cache line even when the external provider backing does not change. Intel i486 documentation says KEN is ignored on writes and write hits update the cache; unconditional invalidation would therefore be an unproven semantic change. Chipset signals and actual guest-visible results need review before adding any per-line policy. See the correction in S17 evidence.

PC110 needs to gate any opt-in on its dynamically observed MISCSET and per-region CBL values and the actual internal shadow read mapping. A change in ROMSET, AAXS–FAXS, CBL, MISCSET, SMRAM or firmware backing must invalidate all affected cached physical views and prefetch through the existing ownership path before subsequent guest execution. MISCSET also potentially affects ordinary RAM cache policy, so only guarding the provider range is insufficient to claim a complete chipset cache-enable model. The source mapping of exact CBL field semantics is an L2/L1 model decision, not a VL82C420 vendor-manual formula.

Each candidate must preserve raw overlay/alias/CPU-only/fallback precedence, provider query failure behavior, single-owner execution, DMA snoop and cache-control side effects; no provider read or guest event may be skipped merely for speed. Measure actual late PC110 workload as well as host time and guest progression: real cache hits reduce guest cycle counts, so increased instruction throughput is not automatically improved virtual clock rate. Test asymmetric read/write, dynamic enable/disable, mapping changes, split-line ranges, fetch versus data, reset, DMA and other receivers. The design is intentionally not yet implemented; the exact provider capability, line policy and global control boundaries remain under audit.

The Intel write-hit evidence eliminates the earlier proposed per-line write-invalidate policy as a default: the existing CPU write-through behavior can remain the single owner unless PC110-specific evidence establishes a chipset-issued invalidation. An opt-in provider fill policy could therefore be smaller: Core first proves the entire line has one observational provider and identical fetch/data view; the provider reports whether the current chipset view permits a cache fill; the CPU retains its existing hit/write behavior. Explicit decode-change notifications are still required to maintain this project's existing view-change contract, and chipset cache-disable signaling must not be equated with an unconditional flush without evidence. This remains a design hypothesis; exact KEN conditions and performance have not been validated.

A task-only four-file prototype provides an opt-in observational provider probe, checks that all 16 bytes resolve to the same provider, rejects providers with a separate instruction-read callback, gates PC110 shadow fill using an explicit provisional L1 interpretation of MISCSET/CBL, and conservatively invalidates the A0000–FFFFF view on successful ECED writes. The existing CPU write-hit path is unchanged. It is not production-qualified: MISCSET effects on ordinary RAM and complete aliases, failure rollback, register-field interpretation, other providers and all regressions remain unverified. An early fixed checkpoint matched baseline at 10,000,000 instructions / 79,964,294 ticks / PC 0003dbc5, when the proposed chipset enable was off.

In one sequential 252-second x64 product comparison, baseline/candidate ended at 664,629,441/613,670,982 guest ticks and 120,232,535/108,061,684 instructions, with 640x480/640x475 sampled frames and RTC second 20/18 respectively. The candidate was slower in this experiment and reached a different guest state, so it is not admitted. Static review found the first prototype checks every byte of a cache line before asking the provider whether a fill is allowed, adding unnecessary work during the disabled phase. A revised task-only prototype checks observational permission first, but still requires a complete route proof before any fill. Neither the original nor revised prototype has passed dynamic edge-case qualification.

Correction to the first product comparison: a task-only 202.5-second diagnostic recorded 53,459,325 provider probes, zero allowed fills and zero F-segment cache hits. Review found that the scratch provider derived CBL indices from 0x13 even though its address range begins at C0000; it must derive them from 0x15. The initial comparison therefore did not exercise the intended cache model and cannot be used to judge its real performance. The scratch prototype was also revised to ask observational permission before performing the 16-byte route proof, retaining that proof for allowed fills. Both changes require new validation; neither has changed production.

The corrected task-only diagnostic, using the C-segment base register 0x15 and permission-before-line-proof ordering, reported 32,615,683 provider probes, 7,843 permitted fills, 78,911,495 F-segment reads and 55,050,508 F-segment cache hits in one 203.02-second run; it ended at 584,480,448 guest ticks, 108,130,371 instructions and a text 80x25 sampled frame. These instrumented counts establish that the path is exercised, not semantic correctness or a final performance result. The first prototype also invalidates the entire A0000–FFFFF view on every successful ECED write, including unrelated or unchanged values. A production candidate must not silently preserve that overbroad invalidation; it needs a precise existing or minimal chipset observation boundary and regression evidence. A separate uninstrumented product comparison is in progress.

## Implemented candidate and initial qualification

The initial production change uses a construction-only optional, observational provider cache probe; undeclared providers retain the existing non-cacheable behavior. Core checks the selected provider and then proves that every byte of the 16-byte cache line resolves to that same provider and contiguous physical view; a provider with an independently installed instruction-read callback is conservatively rejected. Reused provider slots explicitly clear both optional callbacks. The chip exposes its selected index without changing protocol, enabling MyPC110 to invalidate only changed ECED ranges relevant to the provisional cache model. PC110 gates fills on internal shadow, MISCSET bit 3 and the L1 interpretation of the CBL read bit. CPU hit/write implementation and Lib/Emulator remain unchanged. Failure during probe registration removes the newly installed routes. The chipset model does not yet implement MISCSET gating of ordinary RAM and does not claim full hardware cache accuracy.

The existing X86 Core registration test covers default denial, explicit permission and denial, a higher-priority one-byte overlap, distinct instruction-read callback and reused-slot clearing. The VL82C420 test covers selected-index observation and invalid arguments. The existing MyPC110 firmware test uses actual guest CPU reads and writes for both C and F segments: cache-hit write-through behavior, unchanged or unrelated register writes, read-view changes, cache-disable and direct backing inspection. The targeted three-test selection passed on both architectures after the implementation and review. These tests do not establish the full Shared receiving gate, performance for every application or the remaining DMA/snoop and edge cases.

Actual-diff review found and repaired two additional route invariants before full qualification. Reused provider slots now clear both optional callbacks, preventing a new owner inheriting an old callback. A 16-byte CPU fill now requires both bytewise provider agreement and a whole-line route resolving to that same provider; the probe contract also requires a successful, consistent whole-line operational read. The existing Core test covers a provider that accepts individual bytes but declines the complete line. MyPC110 uses a selected-index observation to avoid invalidating cached shadow on unrelated, unchanged or non-read-cache CBL bits. The firmware test uses real CPU read/write behavior for C and F and a DMA write to check coherence, without importing Core-private fixtures. The relevant three tests passed x64 and x86 after these edits. The earlier whole-repository qualification was intentionally stopped upon finding the whole-line gap and is not counted as a pass.
