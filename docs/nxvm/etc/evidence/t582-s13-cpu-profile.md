# T582 S13 — CPU profile-guided optimization experiment

Five existing X86 Core CPU translation units were compiled with GCC 16.1.0 Release flags. A task-owned executable trained them with the existing PC110 fixed-work probe and private CMOS/media, then recompiled the same objects with profile use and no missing profiles. This is a temporary toolchain experiment: profile data and objects remain under the task scratch directory, not product source, build presets, public APIs or releases. The first attempt used a profile directory containing a Windows drive path and produced no data; the corrected attempt used object-local profile files and produced five. Training and every comparison reached 10,000,000 instructions, 79,964,294 guest ticks and PC 0003dbc5.

| Width | Order | Baseline ms | Profile-use ms |
| --- | --- | ---: | ---: |
| x64 | baseline, profile | 20,780 | 17,790 |
| x64 | profile, baseline | 22,248 | 18,644 |
| x86 | baseline, profile | 26,205 | 22,891 |
| x86 | profile, baseline | 28,051 | 23,563 |

These fixed-work observations suggest roughly 13–16% lower time in this early workload, not a full behavior-equivalence proof. The profile was trained on only PC110 startup; it has not been qualified for other Intel profiles, NEC V30, compiler versions or unit/integration suites. Training and repeated compilation have nontrivial build and reproducibility costs. No `.gcda`, guest media or host paths are committed.

A sequential x64 product-path comparison used the same CPU objects, private CMOS/media and 25 ten-second samples. Baseline and profile variants exited zero in 252.61 and 252.47 host seconds. Their last quantum reported 672,816,871 and 745,539,570 guest ticks; RTC reached second 20 and 22. Baseline first recorded graphics at sample 21 and profile at sample 18. Last frame hashes differed, so this is not proof of identical guest state, interactive performance, or full timing correctness. Both paths remain far slower than guest real time.

GCC's PGO output split cold code substantially: in this particular x64 executable, the hot `x86_core_cpu_timing_select` size was 0x5d0 bytes with a separate cold part versus 0x2cc0 bytes without PGO. This is an observation, not proof that this function alone causes the gain. An untrained `-ftracer` candidate measured baseline/candidate 22,361/22,276 ms x64 and 26,387/28,290 ms x86. A separate prototype prevented inlining the existing V30/80186/80286 selectors using a compiler-specific temporary annotation; it measured 21,266/22,380 ms x64 and 27,615/27,843 ms x86. Single ordered pairs do not establish robust regressions, but neither shows a useful gain, so neither is admitted or proposed as production code.

No production code, compiler configuration or artifact changed. Further work must test representative late workloads, both architectures and other CPU profiles, and establish a reproducible profile or simpler portable equivalent without importing protected media or creating another execution path. User-facing desktop/RDP usability remains unverified.

## Repository-test-trained profile experiment

A second temporary experiment trained the same five CPU translation units using 12 existing X86 Core tests rather than PC110 firmware or media. All 12 training runs succeeded on each host width and produced five profile files. On the same 10,000,000-instruction PC110 fixed-work probe, with identical guest ticks and PC, x64 baseline/candidate took 23,360/21,064 ms and the reverse-order candidate/baseline took 20,389/21,596 ms; x86 baseline/candidate took 26,081/23,976 ms and the reverse-order candidate/baseline took 25,310/26,557 ms. These are single ordered measurements, not a whole-product speed guarantee. The 12 existing CPU tests were also linked against the profile-use candidate and passed on both widths; this is targeted coverage, not full qualification.

The x86 profile-use compilation reported a string overread warning when inlining real-mode interrupt entry. Normal INT, external interrupt and exception callers choose that entry only with CR0.PE clear; protected and VM86 entry takes the protected path. The NEC instruction dispatch is restricted to V30, whose reset does not enable CR0.PE and whose Debug register patch rejects CR0. Under those observed invariants, no normal path was found that reaches the eight-byte descriptor copy with the four-byte vector. This static review does not prove all reentrant callback or corrupted-state paths. This evidence does not establish a runtime overread, and does not justify suppressing the warning. A production PGO decision also needs reproducible training, compiler-version compatibility, representative workloads and whole-repository qualification; no build setting or production code was changed.

A shorter x64 product-path comparison used the test-trained CPU profile and separate private CMOS/media copies. The baseline and candidate ran for 62.55 and 62.45 seconds, reported last published guest quanta of 177,277,342 and 189,710,447 ticks respectively, and both ended at RTC second 05. The candidate reached roughly 7.0% more reported ticks in this one sequential early-startup pair. Different execution checkpoints and measurement overhead prevent a claim of identical guest state, late-workload performance or interactive usability. This remains an experiment, not a release configuration. ## Size-optimized CPU code-layout check

A private probe compiled the same five CPU translation units with GCC `-Os`, retaining the existing `-O3` harness and cached product libraries, and compared against the previously directly compiled `-O3` baseline using private CMOS/media. Each completed 10,000,000 instructions at 79,964,294 guest ticks and PC 0003dbc5. Baseline/candidate took 25,104/26,860 ms on x64 and 25,795/28,653 ms on x86. This is one sequential pair per architecture, not a full equivalence or variance study; neither indicates a useful gain. `-Os` is not admitted and the existing Release configuration remains unchanged. ## Repeated prefix classification count

A temporary x64 instrumented copy of the existing CPU timing translation unit counted calls to its instruction-prefix classifier during the fixed PC110 startup probe. It reported 62,388,645 calls and 87,736,172 classified prefix bytes over 10,000,000 retired instructions, ending at the same 79,964,294 ticks and PC 0003dbc5. The instrumentation adds work and counts all classifier callers, not exclusively the 486 cost pipeline; it does not measure exclusive time or prove late workload relevance. The source-cost path independently obtains the prefix index before nominal, memory and decode helpers each obtain it again. A possible local, single-instruction handoff requires checking mutation and independent callers, not a persistent cache or global state. No production source was modified. Log SHA-256: F1D5C7C7B682BD60E82CA3DC665850F13C3C7B191C7B8AE96C40E206D46064F4.

A task-only upper-bound probe reused the prefix count within one 486 source-cost evaluation using a temporary process-global marker. This marker is deliberately not a safe production design: it is not reentrant or thread-safe. At the same 10,000,000-instruction, 79,964,294-tick, PC 0003dbc5 checkpoint, baseline/candidate were 22,700/21,011 ms x64 and 27,245/25,098 ms x86. In reverse order, candidate/baseline were 21,411/23,823 ms x64 and 27,959/27,729 ms x86. The x64 pairs suggest an opportunity, but x86 changes direction and equal checkpoints are not proof of instruction, prefix, REP or debug equivalence. A production candidate must use only an explicitly scoped local value, preserve independent helper contracts and demonstrate actual cross-width benefit; no global marker or source change is admitted. ## Guest cache-control checkpoint

A task-owned probe used the existing paused Core debug-register interface immediately after the fixed 10,000,000-instruction run boundary. The read succeeded and returned CR0=00000010 at 79,964,294 guest ticks and PC 0003dbc5: CD and NW were clear at this early checkpoint. This rules out an assumption that the guest globally disabled the 486 cache at that point, but does not establish late-workload state or that dynamically mapped firmware is cacheable. Machine deliberately admits cache fills only for proven ordinary RAM; the PC110 shadow/Flash provider is dynamically selected by chipset state, so bypassing that boundary is not justified by CR0 alone. No guest state was modified. Log SHA-256: 3F196C7D9446096627914C4378CF2B91BADB218CC7F20025DD5078CC76BFFD2A.

## Worker-specific module sampling

A separate task-owned x64 product-path run sampled suspended instruction pointers during host seconds 5–25 and 220–240, grouping observations by thread and loaded module. Thread CPU-time identified worker 32560 (229.875 seconds CPU accumulated by its last sampling window); it recorded 3,400 early and 3,470 late samples. Of these, msvcrt.dll accounted for 112 early (3.3%) and 177 late (5.1%); ntdll.dll accounted for 2 and 7, with the remainder inside the product image. The previously large aggregate outside-image bucket predominantly reflected other waiting threads, rather than proof that the CPU worker spent most of its time in external libraries. The leading in-image individual symbol buckets remained CPU refresh (207 early / 221 late), memory route resolution (180 / 96), timing selection (101 / 108), and 486 memory penalty (124 / 98). The function buckets are sampled instruction-pointer locations, not inclusive costs; symbols for external DLLs were not resolved.

Sampling pauses threads, enumerated the module list only at startup, and some other threads returned context failures. These facts limit accuracy; it is not a direct wall-time benchmark, exhaustive call graph, or an interactive acceptance. The guest exited zero with private CMOS/media. This evidence does not justify bypassing library calls, hardware events, timing or CPU observations.
