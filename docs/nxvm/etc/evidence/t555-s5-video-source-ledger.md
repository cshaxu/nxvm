## Confirmed Publication Handoff And Design Constraint

`vm_machine_publish_display()` sets `latest_frame_valid` after conversion;
`vm_machine_copy_emulator_frame()` tests that flag and copies the cached frame
on every call. A full source search finds no consumption/clear operation.
Emulator clears staging validity before the driver callback, then publishes
every valid graphics frame; its text-only deduplication is not a graphics
delivery contract. Thus a stable Core graphics cache can generate repeated
consumer publications without a new Core display generation.

The runner also calls `vm_machine_publish_display()` between executor
rendezvous callbacks. Merely returning "no frame" when the next publish call
finds no new chip change would drop a still-undelivered cached frame.
The existing flag can represent pending delivery, with the copied frame's
own validity retaining cache validity; any such repair must consume only
after successful copy. The initial audit proposed this owner-local design;
the implementation and direct/receiving proof below now exercise it. This
does not accept the complete S5. No new Shared API, generation mirror,
frame queue or presentation manager is implied.
