# T582 S24 — PC110 firmware service traffic (in progress)

A hidden x64 product-path probe with private disk and CMOS copies recorded SMM-entry register values on the CPU worker and sampled the restored CPU EAX after the corresponding SMM exit. It recorded bounded aggregates rather than logging every request. Enter was sent through the existing Machine input interface; visual inspection confirmed sample 36 was the World Clock page (00:00:31). Instrumentation perturbs timing and does not exercise native Window/RDP input.

At boot, repeated `AX=5380 BX=8424/840A` calls from linear `0xFDD58` returned low `AX=53FF`; their counts subsequently stopped increasing. This is consistent with existing T580 S48 startup evidence, but does not by itself identify their cause or determine current World Clock behavior. During the sample-30 to sample-36 interval, repeated calls with `AX=5305` from linear `0xFF353` increased from 21,954 to 45,196 for `BX=0004` and from 4,860 to 10,374 for `BX=0098`; restored EAX remained `00005305` in these aggregate records. The report stores only the latest EAX per entry key; it does not yet establish all return flags, the origin before the BIOS handler, or every individual result. Other less frequent `5305` signatures were also observed.

APM defines `5305` as a CPU-idle notification and leaves actual power action to the BIOS. The [General Software Embedded BIOS APM reference](https://files.embeddedts.com/old/saved-downloads-manuals/EBIOS-UM.PDF) is an example implementation, not proof of this IBM PC110 firmware's exact behavior. The observed calls show an important repeated idle-service path; neither their count nor the generic specification proves the current chip model is wrong or that all such calls should be blocked, skipped, or converted directly into HLT. The next step is to trace the actual firmware handler and its device/clock interaction. Scratch guest-log SHA-256: `3E6C68A7DF0133FB45AB4018711DDF98BD45314F65DD525F4A97876BE068B6C4`.


A second private-media x64 run captured one actual `AX=5305` service from SMM entry through `RSM`. The diagnostic recorded 257 retired instruction observations, including the normal SMM dispatcher, the selected APM path and return. No observed instruction in this single trace was `HLT`; the trace contains writes to CPU configuration port 22h and indexed chipset ports 24h/25h, but the single trace alone does not establish all firmware paths or all hardware signals. The APM handler entered an internal AH=04 service; its configuration read produced AH=0Ch and bit 2 selected an immediate FFh branch, consistent with the same existing T580 S48 branch observation. The record is not proof that the branch is a defect or that a particular CPU-idle action is mandated.

A separate short private-media probe captured the producer of the byte read by that internal service. The BIOS copied SCAMP index 58h read via ports 74h/76h to SMM-owned state at physical 30064h; the observed value was 0Ch. The read-only Open-Source-PC110 live SCAMP configuration capture also lists index 58h as 0Ch, as does the existing MyPC110 L2 cold image. A live capture is not a vendor power-on specification and does not establish the meaning of bit 2, but this match is evidence against arbitrarily flipping the value to force another firmware branch. An earlier longer state probe was deliberately terminated after the required writes had been captured; the independent four-sample writer probe exited zero. No ROM, owner media, production code, user configuration or public API was changed.

The firm conclusion is limited: the measured World Clock workload repeatedly calls the standard APM CPU Idle entry, and one observed BIOS handling path executes substantial real firmware before returning. It remains unproven whether other idle variants or a missing chip behavior could alter this outcome. Disabling ASMI, fabricating a successful return, or setting the status bit to a guessed value would hide behavior rather than establish a correct fix.
