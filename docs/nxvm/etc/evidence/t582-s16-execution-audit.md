# T582 S16 — CPU execution observation audit (in progress)

The execution refresh path clears the completed-observation object and invalidates it before each instruction. The existing copy routine fills a zeroed observation after successful timing selection; the timing path can write `next_lexeme_components` before that copy, and the completed value must be retained across asynchronous entry. A scratch-only prototype replaced the full pre-clear in refresh with clearing that one field, retaining the normal later zero-and-fill. Reset behavior was not changed. No production code or public ABI changed.

At a fixed checkpoint of 10,000,000 retired instructions, 79,964,294 guest ticks and PC 0003dbc5, x64 baseline/candidate took 19,782/19,484 ms and x86 26,634/25,418 ms. This is one sequential pair per architecture, not a product-path benchmark; no exceptional, Debug, asynchronous entry or other-profile equivalence has been established. The x64 difference is small, and the candidate would leave old values in the invalid observation object until its next fill. It is not admitted on this evidence. Further investigation must establish the actual owners and cost of instruction, timing and retirement observation before any production design.

Fixed-work log SHA-256: `3620648F5B0F98CD2F4F0E0A9F818CFC2EA172EEAAA9246BBF38844FACB6FC05`.

The sole current caller of `x86_core_cpu_timing_select` passes the context timing result as its output, while the function writes the same result to both. A scratch candidate avoided the second assignment only when the two pointers are identical and preserved the separate-output case. At the same fixed checkpoint, x64 baseline/candidate took 20,154/21,032 ms and x86 25,382/24,827 ms. One ordered pair per width is not a performance guarantee; these opposing results do not justify adding a conditional. The candidate is rejected, with no production changes. Log SHA-256: `E7DE8BDC7B4E7E5F403EE60B49E4488ADBB1886A851FEEE6B89BE36EC7AB9676`.

The complete per-instruction old CPU snapshot also has concrete consumers: invalid opcode and ESC/WAIT restart restore it, and exception and interrupt code uses its saved state. Replacing it with a partial snapshot or skipping it on the apparent normal path would require a proven transactional rollback design for every instruction and callback; the current evidence does not justify that complexity or any such production change.

The formula-input collector currently scans the same byte prefix sequence twice, first to record segment/LOCK flags and then to find the opcode. Two scratch-only single-pass forms were evaluated at the same fixed checkpoint. The condition-chain form measured baseline/candidate 18,759/19,665 ms x64 and 23,358/24,659 ms x86. A switch form measured 21,722/23,012 ms x64 and 27,222/26,506 ms x86. Each was one ordered pair per width; generated code layout and host variation may affect results. Neither demonstrates a cross-width gain; neither has been qualified for every prefix/profile and neither is admitted. Production code remains unchanged.
