## Causal chain

`x86_core_machine_execute_budget()` checks stop, reset, debug, refresh and bus-hold conditions at the instruction boundary. It calls `x86_core_cpu_execution_refresh()` and obtains the CPU timing result. Fault or asynchronous-entry work does not necessarily retire an instruction; external wait and event time may be published separately. Normal retirement is qualified and observed before `x86_core_machine_publish_elapsed_ticks()` publishes its time. Bypassing these boundaries can change faults, interrupt timing, budget exits or debug behavior.

`x86_core_machine_advance_scheduler()` observes the timeline, FPU, CPU wait and board deadlines, chooses the next due tick, advances the shared timeline and arbitration, then calls the board before-internal phase, internal FPU/CPU wait progression and board after-internal phase in that order. The board advances PIT and interrupt readiness before internal time; RTC, keyboard, PIC and video follow. Device callbacks can alter the next deadline. A stable previous deadline alone is not sufficient to batch multiple instructions.

The CPU implementation and board effects must therefore be optimized at their existing owners; removing per-instruction work requires evidence that every observer and mutation boundary remains intact. This record is an audit, not a change to runtime behavior.

## Candidate checked against earlier evidence

When runtime tracing is compiled in, the retirement trace computes the linear PC before the recorder checks its callback. In the standard Release target, however, `X86_CORE_MACHINE_RUNTIME_TRACE_ENABLED=0` makes the trace macro a `sizeof`-only no-op, so neither the PC expression nor the recorder executes. S28 initially overlooked this compile-time distinction. S26 measured an experimental callback guard: [trace audit](t582-s26-trace-audit.md). Its repeated x64/x86 measurements were noisy and did not show a reliable cross-width benefit; the proposed guard duplicates the recorder's admission check. Do not repeat that experiment without a new hypothesis or claim it solves the performance problem. The initial S28 source review rediscovered this candidate before its existing evidence was located; the investigation index now links it.

Further work must identify candidates with clear reduced production complexity or measured material benefit, while proving interrupt, memory, timing, trace and lifecycle ordering. S28 remains active; the whole-product performance objective is not yet met.

## 486 prefix reuse: reconsideration under the owner's complexity criterion

The 486 source-cost owner already computes a prefix count for its opcode; nominal or L2, memory, and decode evaluators then independently compute it again. The exact single-path design was already implemented as a scratch candidate and tested in [the S26 shared-term experiment](t582-s26-486-term-prefix.md): it preserved nine directly affected tests on both widths and reduced production by three lines, but required changes at 125 test calls and two ordered x86 comparisons both favored the baseline. Its x86 regression is not fully characterized; the candidate was withdrawn. It is a bounded scan of the same instruction bytes: the old S5 instrumented workload recorded the overall classifier frequency, not a separate count for these four calls. Passing the already computed value within this one source-cost invocation removes repeated scans, without a persistent cache or a new execution path. Validity requires that the instruction data and CPU mode used by the classifier stay unchanged between those calls; this must be checked on the actual source path, including repeat bookkeeping, before implementation. The bus evaluator and other profiles must retain their own semantics.

The old S5 candidate is not directly applicable to current code: its diff also reverses the later branch-condition simplification, and it removes existing private helper entry points. A naive diff-stat against it is not an estimate of prefix reuse alone. Current focused tests contain approximately 125 call lines to the four helpers, including invalid-argument and isolated timing-term cases. Keeping the old helper implementations as wrappers would retain a second production entry path solely for tests; deleting those tests would lose evidence. The measured single-path candidate made the already-private helpers accept the precomputed count and adapted existing tests to pass a count derived from their fixture. Review must preserve null/invalid input behavior, out-parameter behavior and the distinct nominal, L2, memory and decode assertions. This entailed a material mechanical test diff and the observed x86 direction must be resolved before admission. No public interface change is implied, but all source/test manifest and receiver obligations still apply.

The prior fixed-work and Game comparisons did not demonstrate a reproducible speedup across widths. Under the owner's clarified rule, reduced repeated computation can still qualify if the final implementation remains simple and other properties do not materially worsen; it must not be represented as proven user-visible acceleration. The removed scans are bounded by instruction length and do not change the overall asymptotic complexity of instruction execution. This candidate alone cannot be treated as the PC110 usability fix.

Source check of the 486 repeat bookkeeping: `x86_core_cpu_source_timing_record_repeat()` changes the repeat tracking and `timing_repeat_previous_misses`, but does not write `opcodes`, `oplen`, CPU profile or the saved MD bit used by the prefix counter. That supports reusing the count across this particular call; it does not prove all output equivalence. The four helpers still need their current individual null, exception and stop checks. Repeat bookkeeping itself also counts prefixes; incorporating it would require a separate multi-profile caller audit and is not automatically included in this candidate.

Once the scanner knows the displacement and immediate lengths, it can know the required total byte count before those bytes have all arrived. ## Address-mask plain-span proof

The existing `x86_core_machine_memory_is_plain_span` conservatively rejects every nonzero address-clear mask before its provider-intersection proof. A more selective sufficient condition for a range wholly inside one aligned 16-byte block is: `bytes <= 16 - (physical & 15)` and `(mask & (physical | 15)) == 0`. Every address in that block then has all masked bits clear; whether an individual byte is inside or outside the configured decode range cannot change it. Existing mapping-count, 32-bit wrap, provider-intersection, installed-capacity, RAM identity, parity and observer checks must remain. Other cases continue to use the existing bytewise route; this is not a replacement route or a cache.

A deterministic arithmetic model checked 729,376 exhaustive small-range and seeded 32-bit cases, with varied masks, lengths and decode ranges; 76,950 met the sufficient condition and no accepted range decoded differently. This tests the formula, not the C implementation, provider ordering, cache admission or failures. It does not authorize skipping those checks. Existing tests require extension for masked-bit transitions, decode-range boundaries, narrow provider overlap, address wrap, and read/write and CPU-cache paths before adoption.

The measured S3 startup sample had no active address-clear bits, so this opportunity has no demonstrated relevance to that PC110 phase. The proof only reduces bounded work in qualifying masked spans; it is not evidence of an asymptotic whole-system improvement or of PC110 usability. It is a lower-priority candidate, not the current solution. No production file or executable changed.

## Frozen external wait-window scan

During an external-cycle commit, the existing lookup scans them in registration order, ignores entries whose wait is zero, and returns the first matching active entry. PC110's current configuration does not assign any such window. Source search finds the contract copied during machine initialization, with no production runtime assignment of these windows after initialization.

A scratch candidate stably compacted nonzero windows into the beginning of that existing copied array at initialization, cleared the remaining wait fields, and ended the lookup on its first empty entry. It added no persistent field, interface, guest path or product condition. It is not qualified: tests must cover holes, full capacity, overlapping first-match order, invalid windows, reset and all profile consumers; source-only inspection cannot prove every private direct mutation or observation is absent. ## World Clock SMM refresh cost

A private-media x64 product-path run used the existing World Clock input sequence and sampled approximately one in 256 CPU refresh calls with a pseudorandom selector and host `rdtsc`. Each sample was classified by SMM state immediately before and after refresh: normal-to-normal, normal-to-SMM, SMM-to-normal, or SMM-to-SMM. A state transition within one refresh that returns to the same state would not be separately classified. The probe ran 373.07 host seconds and exited zero; the sample-36 image was inspected and shows World Clock at 00:00:30. Input was injected at Machine, not through a native desktop.

Between the last recorded quanta before samples 30 and 36, host time advanced 59.205 s, guest time advanced 158,376,147 ticks, and 29,228,085 instructions retired. Sample counts and summed non-serialized TSC intervals were: normal-to-normal 86,370 / 205,926,085; entry 114 / 5,767,400; exit 133 / 6,771,395; SMM-to-SMM 28,072 / 69,376,778. These account for approximately 71.54%, 2.00%, 2.35% and 24.10% of this sampled CPU-refresh interval respectively. Entry and exit samples average roughly 50,591 and 50,913 TSC units versus 2,384 for normal-to-normal; sample sizes and host scheduling limit the precision.

These percentages cover CPU refresh only, not scheduler, frame publication, other threads or complete host time. The clock reads are not serialized, instrumentation and frame sampling perturb timing, and endpoints are asynchronous. They do not prove exact component costs or gameplay responsiveness. Nevertheless, this workload does not support treating SMM entry/exit alone as the dominant source of the approximately tenfold guest-clock slowdown: even a hypothetical removal of the measured entry/exit intervals would not remove the normal and SMM instruction execution or board work. Continue investigating the shared execution and advancement path; do not skip SMM memory operations or fabricate APM returns.

## Shift execution candidate for S29

The existing `_a_shl`, `_a_shr` and `_a_sar` each repeat 8-, 16- and 32-bit branches and shift one bit per effective count. The observed Game drawing byte samples include D0 group instructions, but those samples do not distinguish shift suboperations or prove this is a dominant cost. S26 already qualified a constant-work implementation for ordinary ROL/ROR; shifts remain iterative.

A single private shift helper can retain the same caller/decoder and timing owners. It validates 8/16/32-bit width, uses the existing per-profile count, records the same bit/operands/result, and computes the result and final carry directly. Counts zero leave flags untouched. For left/right logical shifts the current CF undefined marker at counts at least width, including the existing V30 exception, must remain exactly as before; carry is the final shifted-out bit, or zero beyond width. Arithmetic right shift sign-extends without signed-C shift assumptions; carry after a count at least width is the original sign bit. OF, AF, SZP, undefined markers, exception behavior for invalid width, and the existing `_kaf_set_flags` calls must match the original per direction. No decoded timing, instruction count, bus access, interface or state is changed.

Compare timing and observation fields, not just results. A model comparison alone is not CPU proof. Build and run targeted x64/x86 tests first, then use the cached Shared receiving gate and fourteen receiver artifacts if implemented.
