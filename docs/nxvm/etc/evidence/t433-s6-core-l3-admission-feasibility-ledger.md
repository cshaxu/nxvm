# T433 S6: Core L3 Admission And Feasibility Ledger

`M5:T433:S6:L3-ADMISSION-LEDGER:OK`

## Decision boundary

This corrective ledger consumes exactly the 30 frozen T433 capability IDs.  It
turns each prior summary disposition into a downstream implementation contract:
the actual missing fact, whether neutral Core can host a documentation-driven
L3 rule, the required plan/program declaration, and the proof that removes the
row's L2 exception.  It does not claim that the rule has been implemented.

**L3 is feasible in Core.**  Here that means a documented constant, formula,
bounded range with a deterministic selection, or labelled reference-derived
contract, scheduled by Core's existing virtual clock.  It does not mean pin
waveforms, propagation measurement, or a universal clone; those are L4 and
are neither required nor admissible.  A `conditional` row is implementable by
Core, but cannot receive a number, deadline, or phase transition until the
named primary/manual or qualified reference fact is admitted.  An `outside`
row is intentionally not a guest-time capability and is not an L3 deficit.

The future copied `core_machine_plan` uses the conceptual fields already fixed
by the timing design: `clock_domains`, `cpu_program`, `transactions`,
`arbitration`, `devices`, `lifecycle`, `observation`, and `l2_exceptions`.
Those names describe required plan content, not a prematurely frozen C ABI.

## Reconciliation and admission rule

Every current hardware-facing row is therefore either **Core-feasible** or
**Core-feasible after a named manual/reference admission**.  None requires L4
work.  The six integration/product rows that are outside guest time are not
hardware timing gaps and must remain excluded from L3 counts.

The next timing-plan task must first implement validation and copied lifetime
for the declaration groups above, retain an explicit default L2 plan, and
reject an unregistered rule.  It must not allocate a device number.  The
following CPU, transaction, and controller/device tasks may then close a row
only by admitting the stated evidence, implementing its rule through the named
Core owner, and passing the stated focused proof.  A missing fact remains an
`l2_exceptions` entry; a successful boot, generic tick, host delay or emulator
default cannot remove it.
