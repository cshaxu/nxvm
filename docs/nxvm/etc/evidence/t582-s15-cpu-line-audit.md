# T582 S15 — CPU source-line sampling

A task-owned x64 executable linked the five current CPU translation units compiled with the same `-O3` Release configuration plus debug information. Its ordinary PC110 factory/worker path used private copied CMOS/media. A Windows sampler recorded thread instruction pointers in the host-second windows 5–25 and 220–240; worker thread 8048 was selected by its cumulative processor time (230.125 seconds at the last window). The run exited zero. Decoding used the matching x64 objdump's DWARF line output because the default PATH `addr2line` was a 32-bit tool.

The worker had 3,304 early and 3,336 late in-image samples. Line resolution left 1,642 in each period unknown because only CPU translation units carried source-line information; objdump also warned of a corrupt file-name list, so attribution is indicative and requires validation. Among mapped lines, prefix dispatch in `cpu_instructions.c:3151` had 64 early / 45 late samples; prefix count in `cpu_timing_model.c:22` had 53 / 24; `types_interface.h:77` (the memory-copy facade) had 37 / 52; the entry-scope call in `cpu_instructions.c:21943` had 17 / 35; cache-way lookup in `cpu_instructions.c:331` had 20 / 27. These are instruction-pointer counts, not inclusive timing and not CPU-wide percentages. The symbol and line layout can change under instrumentation, sample windows are host-time based, and the sampler pauses threads. Unmapped non-CPU code and other modules cannot be inferred from these numbers.

The 486 execution path currently begins and ends an instruction-event access scope for every retired instruction before asynchronous entry arbitration. That scope copies and resets the completed instruction's timing counters so interrupt, Debug and other event entry cannot overwrite the source instruction's facts. There is a possible lazy-scope optimization only if it starts at the exact existing event boundary and also preserves SMM, special cycles, flush, Debug, NMI, interrupt acknowledgement/failure, recursive faults and counter restoration without a second arbitration path. The current observation is not evidence that a speculative pre-check or skipping this scope is correct. The earlier prefix-local candidate did not improve sustained PC110 product throughput, and a blanket cache or memory-copy bypass is not justified. No production source or EXE changed in S15.

A task-owned x64 counter probe observed 10,001,409 retired-486 outer event scopes in the fixed startup run, of which 9,995,296 had none of the conservatively marked flush, SMI, Debug, NMI, accepted interrupt or special-cycle conditions. It recorded 6,103 SMI-pending and 10 accepted interrupt markers; categories can overlap and the SMI marker is a conservative pending indication, not proof of accepted entry. The fixed checkpoint remained 10,000,000 retired instructions, 79,964,294 ticks and PC 0003dbc5. The extra counters perturb runtime and global probe state is not production-safe. This suggests most scope copies occur without a marked event, but does not prove that all unmarked callbacks are observational, that late workload behaves alike, or that deferral is safe. Log SHA-256: `1B5C9213CB793415C15434F35C14CA57B3261118DDCE1ECDD622AD30EC17BD77`.

A separate task-only lazy-scope prototype kept the existing event arbitration, started the same scope conservatively for pending flush, SMI, Debug, NMI or special cycles, and started it after the existing interrupt-pending query but before acknowledgement. It did not add a global state or second interrupt poll. This prototype is not qualified: the generic interrupt callback observation and all nested entry, special-cycle and failure paths need proof. At the identical fixed 10,000,000-instruction, 79,964,294-tick, PC 0003dbc5 checkpoint, baseline/candidate times were 20,989/21,043 ms x64 and 24,962/24,531 ms x86. These are single sequential pairs; the small and inconsistent benefit does not justify the added event-scope complexity. It was not admitted and no production code changed. Log SHA-256: `A861688106832D66A15806B324630F7D9038CAD2A6F7DFAE7D0A2B5AF4B18175`.

The original PC110 worker samples were additionally mapped against the matching Release-equivalent memory object. Its `.text` bytes match the Release object; the source-line mapping remains an approximate sample, not inclusive attribution. Remaining candidate collection at `memory.c:125` accounted for 30 early / 25 late samples and raw-overlay scanning at `memory.c:86` for 28 / 17. This does not establish the cost of either entire loop.

A task-only candidate combines those two provider traversals into one local pass, retains the existing raw-overlay, selected-alias, replacement, ordinary and fallback precedence, and adds neither persistent state nor an API. It computes address decoding before observational raw queries; correctness depends on the existing observational-query and owning-executor contracts. At the same 10,000,000 instruction / 79,964,294 tick / PC 0003dbc5 checkpoint, x64 baseline/candidate took 19,982/19,071 ms and x86 24,904/24,103 ms, respectively one sequential pair per architecture. Six existing memory route tests passed on each architecture with the candidate linked in. These fixed-work and local tests do not establish a sustained product-path benefit or comprehensive semantic equivalence; those remain under examination. No production code changed.
