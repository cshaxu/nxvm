# T580 S52 - SL power findings and RTC address-space receiver

## Frozen baseline and new primary source

Baseline is pushed `013b58329`. S51 establishes the executed cold FB clear,
later FB=00 guard, vendor power request, finite checksum and suspend HLT.
This record does not turn that prefix into POST, Setup or product success.

The newly acquired original reference is *Intel's SL Architecture: Designing
Portable Applications* (1993), public
[Bitsavers mirror](https://bitsavers.trailing-edge.com/components/intel/80486/Intels_SL_Architecture_Designing_Portable_Applications_1993/Intels_SL_Architecture_Designing_Portable_Applications_1993.pdf).

The 23,530,066-byte manual is archived outside Git with the other CPU manuals.
It has 352 PDF pages. Printed page 69 is PDF page 88 and was rendered and

## Constraints established, not guessed

The original Intel reference distinguishes global standby, retained-power
suspend, zero-power suspend, and SMM return. Global standby can continue at
the instruction after the clock-stop operation when a qualified break event
occurs. Suspend resume instead follows an external event and reset-vector
firmware restoration. Its listed event sources include the suspend button,
modem ring and RTC calendar. Retained-power operation preserves powered
static state; zero-power operation needs saved system state. These facts
constrain a PC110 L2 model; they do not make its registers Intel-identical.

In particular, Intel's SPND_STS and RESUME_MASK definitions cannot simply be
assigned to PC110 B8/BC. The PC110 research record gives BC refresh-related
uses and leaves FB's bit meaning hypothetical. Index equality is not source
evidence for bit equality. No hardware-accurate delay or new numeric timing
constant is admitted from an analogy.

## Complete firmware and implementation boundary

| Member | Actual evidence | Consequence |
| --- | --- | --- |
| FB | Firmware clears it in cold initialization and again before HLT; later tests bit 3. The live capture is 18h, not a power-on specification. | Do not freeze it high, suppress the guest clear, or call it a read-only power-good strap without a receiver contract. |
| B8 | Firmware clears it before HLT and tests bit 3 at reset entry. | Any resume cause must be generated by a specified real board event and consumed by firmware, not copied from the live capture on every reset. |
| FF | Actual guest writes 82h immediately before HLT. | The current plain register file records the command but does not implement suspend/wake side effects. |
| Mode 22h | Guest opens the existing byte/word protocol, selects the memory unit and writes 0083h. | Preserve the single App-owned unit/configuration owner. Do not add a second copy of this register to the chipset. |
| HLT continuation | Static bytes at copied 39334 are STC/LRET, not an endless self-jump. | That is a software error/continuation path, not proof that an arbitrary interrupt should release suspend. No generic HLT repair is justified. |
| Restoration | Copied routine 39336 reads FB again, checks bit 3 and restores saved CPU/chipset state. | Correct testing must include the existing BIOS restoration route, not only a reset or a cleared HLT bit. |
| Core | Public stop-clock, clock-running, SMI and processor-reset inputs already exist. | Reuse them when their contracts fit. None supplies a PC110 power-button source or automatically implements the board's retention/reset selection. |
| EC/planar | Existing mailbox and 35EA/35EB bank provide bounded static L2 behavior, not a live power controller. | A new generic manager or host completion is not a replacement for the missing physical input/status receiver. |

The BIOS addresses above are evidence anchors only. No production behavior
may branch on those addresses, task markers or the selected firmware hash.
The image and font remain unchanged. Static disassembly maps file 29000h to
copied address 38000h, and file 30000h to ROM F0000h; these are distinct views.

## Reference-model reconciliation

The pinned QEMU register receiver remains a plain read/write file and its
separate CPU-side source includes firmware redirects and resume interception.
The pinned PC110-EMU source similarly contains BIOS-specific HLT releases and
Setup-only register forcing. Those behaviors are not portable chip contracts
and are not imported. Their existence explains why reference boot success
does not prove that a complete physical power receiver has already been
specified for reuse here.

The current [MAME VL82C420 source](https://raw.githubusercontent.com/mamedev/mame/master/src/devices/machine/vl82c420.cpp)
was also checked as a read-only reference, SHA-256
`7E0E57D31545D39C0EE008D662621DEBE6E30139B9436319B0E438A6253B8322`.
It declares missing VL82C420 documentation and does not implement this
Block-2 suspend/resume receiver. Its PMRA/PMRE names mean programmed memory
region address/enable, not power-management registers. It
therefore supplies no complete wake model to adopt. Its BSD-3-Clause source
is not copied into tracked source, translated, linked or used as a runtime
dependency. No emulator's boot claim substitutes for reviewing its receiver.

Open-Source-PC110's power sequence identifies the separate U6 power MCU,
enable outputs and handshake; the Pluto/Bowman records distinguish that MCU
from the keyboard MCU and warn that telemetry attribution remains partly
inferred. The board's real wake wiring must be reconciled with that distinction.
The research is allowed to select a bounded explicit L2 model; no physical
unit trace is required as a blanket precondition.

## Design ownership and proof obligations

The smallest candidate uses the existing chipset register owner for chip
power/status effects and the App for the selected physical event and its
wiring. Core remains the only executor/timeline and CPU state owner. Monitor
pause/resume is not redefined as a power-button edge. Existing App mode-22
state must not be mirrored. No Lib/Emulator change is justified by this audit.

Before implementing a suspend/wake receiver, settle these connected questions:

1. Which board-produced status changes FB/B8, under which input and guest
   write semantics? A live 18h capture alone is insufficient.
2. Which actual input initiates the first wake, how is it armed/consumed, and
   does the selected retained-power transition require processor-only reset
   or a wider board reset? No automatic wake solely because HLT was reached.
3. Which RAM/SMRAM, CMOS, configuration and decoder state survive, and how
   does unchanged reset-vector firmware enter its genuine restoration path?

The eventual existing-fixture proof must cover cold entry, guest command,
no-event suspension, qualified wake, cause acknowledgement, retained state,
and restoration in one batch on both widths. A test that only injects reset
or reaches the previous HLT is not that proof. These questions remain active
research; this record is not a completed power implementation.

## Actual RTC and NVRAM observations

The temporary sampler in the existing real-BIOS harness records only executed
I/O observations, without reading RTC C itself or adding a guest event.
The x64 unchanged-BIOS run again reaches the real HLT at 39333h after
32,019,076 instructions, three processor resets and the four known delivered
GP probes. Last observed RTC A=26h and B=02h: AIE is not enabled. Alarm
registers 01h/03h/05h have no observed access in this run. Consequently an
already-programmed alarm cannot be assumed to supply the missing first wake.
The diagnostic exits normally; this is evidence of suspend, not successful
product boot or a corrected power receiver.

The same observation exposes BIOS accesses above CMOS 3Fh. Actual Board code
unconditionally masks the address with 3Fh; its RTC has only 64 bytes. Both
pinned external models instead keep 128 CMOS bytes and mask with 7Fh. This
supports a bounded compatible-128-space L2 correction, not a new silicon
timing claim. The external source concepts are reviewed; no implementation
text is imported or translated.

Separate 17-instruction guest programs execute through the actual Product
construction's CPU/Board routes on both widths: write 55h to 3Bh, AAh to
7Bh, then read both into RAM. Both baseline executables return AA/AA, directly
proving the alias independently of any BIOS branch. Those probe exits confirm
the reproduced defect, not a passing functional requirement. The repaired
receiver must instead yield 55/AA.

## Capacity receiver and retained path

Coordinator review selects one RTC-owned 128-byte capacity, with copied
construction selecting classic 64 or extended 128. Existing Boards retain
classic zero-default behavior, including their old address alias; PC110
explicitly selects extended decode. Calendar, IRQ, reset retention and NMI
remain with their existing owners. No second upper-CMOS array or App port
override is added. A normalized selection field is appended to the existing
RTC and Board configs; no public function or callback is added. Lib,
Emulator and X86 Core are untouched.

The existing RTC RAM/reset test covers all selected addresses for both
variants; the existing Board test covers old alias versus extended isolation,
upper defaults, NMI separation and invalid configuration. The existing App
construction test verifies the real adapter's distinct 3B/7B values. Temporary
guest samplers are removed; the original integration source has zero diff.
There is no second NVRAM store, shadow register file, lifecycle queue, new
public function, helper, thread or clock. The one added private byte is the
immutable construction-selected register count, not a power-state machine.
The two public config additions use existing lib_bool and reject values
outside LIB_FALSE/LIB_TRUE. Old defaults remain classic; no App name or ROM
address is recognized by Shared.

## Actual verification

- Both guest-IN/OUT probes now return 55/AA after exactly 17 instructions.
  The two baseline logs are byte-identical, as are the two repaired logs.
- The 19 focused RTC/PC110 units pass per width: x64 13.86 s, x86 2.07 s.
- Complete repository unit sets pass in their first invocations: 712/712
  x64 in 337.01 s and 712/712 x86 in 220.47 s. No assertion, timeout or
  source change is made between these complete runs. This includes the
  unchanged Lib/Emulator/other-App tests, not just the changed receiver.
- The repaired actual BIOS reaches 39334h after 32,019,249 instructions on
  both widths. Its complete two logs are byte-identical. RTC B remains 02h,
  three resets and four delivered GP probes remain, and timer delta is 166Ch.
  This disproves any claim that the capacity repair alone solves suspend.
- After removing the temporary sampler and rebuilding the original harness,
  both widths pass --fdc-reset: 11,613,024 instructions, F7490h, successful
  initialization/ASMI/service/RSM, timer delta 166Ch and all four reset SENSE
  results. No original success condition is weakened.
- All eight receiving PC EXEs rebuild and deploy at 0.5.0580. Their PE width,
  embedded version string and each actual adjacent-INI integration pass.
  Owner INI hashes match the pre-build hashes below. No external ROM/media
  or MyNES/MyRaidenII private source or deployed binary changes.
- Four PC110 TFT/derived-DSTN previews rebuild only under the existing stable
  Ninja trees; they are not deployed as qualified products. Both final
  build-unit-tests/preview incremental builds report no work to do.
- Both changed manifests, complete unit boundary/type checks, NXVM document
  governance and git diff --check pass. No new warning exemption is added.

Two product-loop orchestration mistakes are distinct from qualification:
an abbreviated DeskPro profile is rejected, then the exact admitted key is
used; a misplaced PowerShell redirection fails after both remaining x64
builds and INI tests have already passed. Neither is counted as a product
test pass or hidden as a source fix. The corrected x86 loop uses scoped
redirection and completes normally. No successful earlier group is rerun
just to obtain a prettier wrapper exit status.

No desktop/RDP, PC110 panel, Easy-Setup, INT 19h, selected guest boot or full
live lifecycle acceptance is claimed. The separate DSTN input is still a
documented derived image, not an independently recovered factory dump.

manifests, documentation and binaries: production +27/-7 (net +20), tests
+83/-34 (net +49), total +110/-41 (net +69). Shared is +96/-38; NXVM App

The sweep uses rg over src/test for rtc_selected_register, both register-count

uses are unrelated and unchanged. Classic Board aliasing is intentionally
retained and tested as a distinct admitted hardware variant, not a duplicate
receiver. The existing RTC test extends its RAM/reset cases rather than
adding another independently maintained RAM test.

| Member | S52 disposition |

| Existing mode-22 protocol | S47 access-width proof retained; no duplicate mode state or new CPU behavior. |
| RTC automatic wake hypothesis | Rejected for this actual cold run: AIE is not enabled. |
| Cold FB, B8, FF and SMM/HLT observations | Corroborated without forced status, ROM mutation or instruction bypass. |
| Physical wake/status transaction | Still unimplemented; source-index equality, a live capture or emulator firmware interception cannot supply its bit/write/reset contract. Earliest receiver remains the App/chip power wiring inside T580. |
| Original product/guest gates | Unchanged and open; this bounded correction qualifies none of them. |

The next power implementation must cover a named real event, its chip-visible
status/cause, retention, reset and unchanged firmware restoration together.
It may use an explicitly justified L2 model; no physical-unit dump is imposed
as a blanket prerequisite. It must not invent an unconditional first wake or
reinterpret monitor pause/resume as that physical event. This is a precise
remaining design boundary, not a claim of completed power management.
