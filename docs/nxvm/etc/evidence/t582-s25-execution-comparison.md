# T582 S25 — PC110 execution and clock reference comparison

This is a static, read-only comparison against clean local PC110-EMU `81235b5` and PC110-QEMU `bae390e` checkouts; neither external emulator was built or timed in this S, and their performance is not measured here. The observed NXVM baseline is the actual Personaware World Clock probe in S19: approximately six guest seconds per 60 host seconds on this host, with timing, RTC and device service tied to the guest execution timeline. That result is instrumented and is not a desktop/RDP qualification.

PC110-EMU's `pc110_rtc_datetime` obtains its RTC from an initial host `time()` plus elapsed `gettimeofday()`-based host milliseconds when that clock is available; its INT 1Ah path also implements BIOS clock services in the emulator. This explains how its displayed clock can advance independently of interpreted guest instruction throughput, but it does not establish that the emulated CPU executes faster or that every timer, interrupt, pause, or machine-clock contract is equivalent to NXVM. Its core also contains explicit BIOS/guest shortcuts, including selected HLT handling and synthetic DOS/BIOS services. No such path was adopted.

PC110-QEMU's real-BIOS launch script uses QEMU with `-cpu 486` and `-icount shift=5`; its README describes TCG execution with an approximately 32 ns fixed virtual time per instruction, and explicitly describes optional POST completion and INT 13h/19h service helpers. The project's custom chipset file models some clock-stop registers as latches without stopping the processor, and its `cmos_get` returns stored CMOS bytes for ordinary time registers rather than implementing a ticking RTC in that function. We did not run that project, prove the timing of its World Clock, or attribute its observed UI to an unmeasured particular feature. A per-instruction fixed step is not a demonstrated equivalent to the NXVM 486 timing ledger; changing the selected timing model would require the owner-approved accuracy-downgrade process. TCG's translated execution model is substantially different from the existing NXVM interpreter and is not a drop-in source or a demonstrated semantics-preserving optimization.

The differences are useful as architecture references, not evidence that host-time substitution, bypassing firmware or replacing existing timing facts are safe repairs. No production, public interface, EXE, firmware or user media was modified. The governing T currently excludes host-time substitution, skipped guest work and a second executor. Achieving the desired order-of-magnitude throughput with those guarantees has not been demonstrated by S19–S24's measured microcandidates; one cannot infer impossibility from that evidence. A next design must either demonstrate equivalent execution with a substantial speedup, or clearly propose and obtain the required approval for any timing/behavior tradeoff rather than quietly weakening the contract.

These inputs stay in their existing read-only external checkouts; no third-party implementation was copied.

NXVM currently advances its RTC through the board's `rtc_clock` from guest `source_ticks`, then calls the existing RTC device advance path; timers, interrupt scheduling and time publication share the guest timeline. Making only the RTC follow host time would address a visible clock symptom but would not make CPU execution faster, and would require deliberate answers for pause, reset, alarms/periodic IRQ, PIT/DOS time and reproducible execution. It would contradict the currently admitted T582 no-host-time-substitution constraint without a separately reviewed scope change. Likewise, assigning a constant cost to each instruction is a timing-model change, not a mechanical speed optimization. No recommendation is made to adopt either tradeoff on the present evidence.
