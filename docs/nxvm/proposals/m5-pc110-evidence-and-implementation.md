# PC110 Evidence And Component Implementation

## Goal

Deliver the actual IBM Palm Top PC110 through the existing Core and Emulator
runtime. Initially admitted as M5 T558 on 2026-10-13. The owner subsequently
requested a multi-T plan: T558 now owns research and contract freeze; the nine
implementation/qualification receivers below carry the complete product goal.
All candidates remain M5. This is an explicit scope split, not a claim that
research alone completes PC110. The owner accepted research delivery 7ea9084fe
and closed T558 on 2026-10-13 with the S2 decision gates explicitly transferred
to their named receivers. T559 starts with the CPU inventory/decision batch;
the remaining proposals stay unnumbered until admission.

## Current Product Context

[four-App migration](../history/M5-T543-four-pc-apps-proposal.md), not a runtime option of XT, AT,
DeskPro or default PC/AT. It has two build-fixed compositions over one shared
PC110 implementation: original DSTN and TFT-upgraded. Each executable uses
one frozen machine/firmware pairing, a lawful external
BYOB asset root and an adjacent INI for runtime media/presentation. Its product
scope and sole artifact directory must be admitted under the App cutover
governance, not assumed to be the current `assets/nxvm/<profile>/` route.
Nothing here claims that the current four-product sources or assets implement
PC110 yet. Raw ROMs remain in the external nxvm-assets archive. By explicit
owner authorization they may be embedded at build time into the committed
`assets/mypc110/mypc110_x86.exe`, `mypc110_x64.exe`,
`mypc110_tft_x86.exe` and `mypc110_tft_x64.exe`. These exact owner-selected
filenames omit the version; the product's internal version remains tracked.
Generated byte sources
remain ignored; the adjacent `mypc110.ini` configures runtime media/presentation,
not firmware paths. This does not authorize acquiring unrelated firmware.

### Two Fixed PC110 Variants

The owner first proposed INI-selected external BIOS loading, then superseded
that proposal with two compiled models and the four filenames above. Do not
implement runtime model selection, external BIOS loading or firmware fallback.
Both variants share `app-mypc110` mechanisms and common construction; only
genuine panel configuration, identity and firmware binding differ. BIOS and
other required ROMs remain external build inputs and are embedded in each EXE.
One adjacent `mypc110.ini` retains runtime RAM/media/presentation settings, not
the selected panel or BIOS. Construction freezes the compiled variant; reset
reuses it. This is not a second PC110 runtime, parser or lifecycle owner.

Qualify DSTN and TFT independently on both host widths. The inspected TFT
candidate cannot silently serve the DSTN build. The confirmed author-supplied
bidirectional panel patch provides an offline preparation candidate alongside
the search for an unchanged original dump. Follow the
[patch evidence and qualification gates](../etc/evidence/t558-s2-source-availability.md#bidirectional-panel-patch-source-confirmed):
freeze input identity, applicability, exact differences and integrity before
admitting preparation; record a restored image as derived rather than pristine.
Preserve external master bytes and verify each executable's embedded pairing.
Patch reversibility does not replace independent guest boot qualification.

## Evidence First

Freeze board revision, CPU variant, chipset, memory map, display/LCD, storage,
PCMCIA, keyboard/pointer, audio and power behavior plus every firmware slot.
Distinguish IBM/manufacturer originals, observed dumps, reconstructed documents,
emulator models and placeholders. The current external PC110 research tree
does not prove complete original chipset documentation or a bootable emulator.

## Stop And Exit

Do not claim physical accuracy from a reconstruction or from an emulator's
placeholder. Missing sources may support labelled L2 with evidence, never
invented L3. Source gaps requiring product exclusion or owner choice are reported.
A build alone cannot close PC110; accepted guest and lifecycle checkpoints
are required under the normal unit/integration/artifact rules. T558 itself is
design-only: closure proves the frozen design and named receiver map, not a
PC110 executable or boot. Missing required source/model decisions block the
affected implementation admission instead of becoming guessed behavior.

## Research And Implementation Gates

S1 inventories sources, actual code and assets and establishes the
[convergence ledger](../etc/evidence/t558-s1-pc110-source-and-gap-ledger.md).
It does not implement a machine or claim hardware qualification. Its coverage
domains transfer to the named T receivers above; their S boundaries are fixed
at admission from the ledger, with large batches split before implementation.

The [Core/App ownership audit](../etc/evidence/t558-s1-core-app-ownership.md)
maps existing four-App boundaries and the PC110 receivers. Independent chip
mechanisms belong to Core even with one consumer; PC110-specific wiring,
firmware roles and board glue belong to the App. Freeze uncertain identities
before selecting a chip boundary. Reuse the existing Core execution timeline,
Machine driver and PC Product/Emulator route; no second executor, host BIOS/DOS
interception, fabricated ROM, universal device framework or Shared change is
implicitly authorized. First freeze a concrete board and firmware inventory;
missing documentation remains an explicit research item, not stub success.

Overall product completion requires all ledger domains to have direct proof or owner-approved
exclusions, real firmware reset/POST/setup/guest checkpoints, input/display and
storage proof, lifecycle/failure cleanup, both host architectures, full required
tests, verified releases and acceptance. A future S must freeze the exact guest
media/checkpoints before implementation claims boot compatibility.
