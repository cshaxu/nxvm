# M5 T139: Win32 Platform Run Handle

| Subtask | Scope | Status | Evidence |
| --- | --- | --- | --- |
| S1 | Define the run-handle API and move ownership from Win32 backend-local contexts to VM session composition | Complete | `docs/verification/m5-t139-s1-win32-run-handle.md` |

## Boundaries

- **Objective:** a session-owned handle is the sole owner of Win32 kernel and
  display thread handles, run state, renderer/window state, and teardown.
- **Non-goals:** change retained NXVM Console commands, make execution
  single-threaded, alter guest boot sequencing, or add VDM behavior.
- **Reference:** T138 current-owner map and `nxvm_0_5_0139.exe`.
- **Gates:** dependency-DAG configure; run-handle lifecycle tests; Console
  lifecycle; normal stop; repeated cancellation; partial worker-start failure;
  two-session host-surface contention; FDD DOS prompt.
- **Stop:** stop on a worker freeing shared state, session finalization with a
  live handle, Console/window startup regression, or FDD DOS-prompt failure.

## Result

`vm_session` embeds the sole `vm_platform_run_handle`. The Win32 Console and
window implementations place both worker handles, renderer/surface lifecycle,
and backend-local data behind that owner. Workers only start/stop guest work or
report window closure; only the session lifecycle joins workers and finalizes
the backend. The retained Console keeps its historical synchronous `start`
ownership; asynchronous window `stop` uses the same request-stop then
join/finalize order. T140 owns the equivalent Linux conversion.
