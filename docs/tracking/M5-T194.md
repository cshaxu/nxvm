# M5 T194: Platform Run-Event Boundary

Status: complete.

## Objective

Make the existing session-owned platform run handle the sole owner of run
lifecycle state while making worker-to-composition reporting explicit. A worker
may report cancellation, completion, or startup failure; it may not call the
VM execution control or release shared resources.

## S1 Contract

- `vm_platform_run_handle` owns the last copied run event for one live run.
- `vm_platform_run_handle` is the cross-thread notification boundary; it is
  not a machine handle.
- Composition consumes only a cancellation report at its execution boundary
  and performs the guest stop there.
- Guest completion and display completion are recorded but do not enqueue a
  later stale stop against a subsequent run.
- `vm_session_stop` and `vm_session_finalize` remain the only request-stop,
  join, and finalization callers. Retained NXVM Console stop/start semantics
  must not change.

## Planned Subtasks

- **S1:** record this contract, owner map, source surface, rules, gates, and
  stop conditions.
- **S2:** add the common event/reporting API and route worker cancellation
  through the request transport without changing native resource ownership.
- **S3:** add common state/order smokes and Windows GCC gates; produce
  `nxvm_0_5_0194.exe` after runnable-path verification.

## Boundaries

- No new thread, session, event loop, or core/platform dependency.
- No changes to NXVM Console grammar, boot media, debugger, or display mode.
- No test-only global selector or release-path failure switch.
- Applicable rules: single state owner, worker reporting only, composition-only
  integration, no platform guest-state mutation, wrapper discipline, and one
  task-level artifact.

## Planned Evidence

- Common report/queue/command-boundary smoke.
- Existing run-handle, two-window, Console lifecycle, keyboard, FDD DOS prompt,
  dependency-DAG, facade, session-readiness, and lifecycle gates.
- Source scans proving that display/input workers no longer call
  `vm_platform_execution_stop_for`; the designated kernel worker is the only
  source permitted to call `vm_platform_execution_start_for`.

## Stop Conditions

Stop and repair before continuing if a worker frees a native/shared object,
platform code includes VM machine/control state, a completion event can stop a
later run, a second run handle/session is introduced, or retained Console,
debugger, boot, keyboard, or DOS-prompt behavior regresses.

- `vm-platform-run-handle-smoke` emitted `M5:T194:S3:RUN-EVENT:OK`. It proves
  a completion event cannot request a stop, one explicit stop report is
  consumed once, and a live window session stops through the runner boundary
  before reset and a later clean run.
- The retained interactive artifact accepted piped `EXIT`; the banner was
  `Neko's x86 Virtual Machine [0.5.0194]`.
- `nxvm_0_5_0194.exe` SHA-256:
  `A04CFBAA34FC13DB6C17440848A0F5AD30DBA9397EFAF60BD120E24109E0ADC0`.
- Static review found platform calls to `vm_platform_execution_stop_for()`
  only in the explicit backend request-stop functions; display/input workers
  report events and do not release handles, renderers, or contexts.
